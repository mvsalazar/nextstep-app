# NextStep API (v1)

This document specifies the API required by the NextStep app in API mode. It is designed for a single authenticated parent/guardian (“owner”) who manages one or more child profiles. All data are owned by the parent and scoped by `childId` where applicable.

Base URL
- Base: `/api`
- Version: `/v1`
- Full example: `https://your-domain.com/api/v1`

Conventions
- Auth: Bearer JWT in the `Authorization` header.
- Content type: `application/json` for requests and responses unless noted.
- Error format: `{ code: string, message: string, details?: any }` with appropriate HTTP status.
- Ownership: Owner inferred from auth token; server must enforce that `childId` belongs to the current owner.
- IDs: String identifiers generated by the server unless noted.

Authentication

- POST `/auth/signup`
  - Body: `{ email: string, password: string, name?: string }`
  - 201 → `{ token: string, user: { id, email, name?, role: 'parent'|'guardian' } }`
  - 400/409 on invalid or duplicate email

- POST `/auth/login`
  - Body: `{ email: string, password: string }`
  - 200 → `{ token: string, user: { id, email, name?, role } }`
  - 401 on invalid credentials

- POST `/auth/logout`
  - 200 → `{ success: true }`

- GET `/me`
  - 200 → `{ id: string, email: string, name?: string, role: 'parent'|'guardian' }`
  - 401 if not authenticated

Children (Managed Profiles)

- GET `/children`
  - 200 → `ChildUser[]` where `ChildUser = { id, name, emoji?, parentId }`

- POST `/children`
  - Body: `{ name: string, emoji?: string }`
  - 201 → `ChildUser`
  - Server should clone default routines/templates for the new child or create an empty set (implementation choice).

- DELETE `/children/:id`
  - 200 → `{ success: true }`
  - Removes child and their routines/tasks; adjusts current selection if needed.

- PATCH `/children/:id` (optional)
  - Body: `{ name?: string, emoji?: string }`
  - 200 → updated `ChildUser`

Routines

- GET `/routines?childId=...`
  - 200 → `Routine[]` sorted by `order` ascending
  - Routine = `{ id, ownerId?, childId, name, emoji, color?, active, order, updatedAt?, version? }`

- GET `/routines/:id`
  - 200 → `Routine`
  - 404 if not found or not owned by user

- POST `/routines`
  - Body: `{ childId: string, name: string, emoji: string, color?: string, active?: boolean }`
  - 201 → `Routine`
  - Server assigns `ownerId`, `order`, timestamps, version.

- PATCH `/routines/:id`
  - Body: Partial of Routine (excluding immutable fields like `id`, `ownerId`)
  - 200 → updated `Routine`

- DELETE `/routines/:id`
  - 200 → `{ success: true }`
  - Also deletes associated tasks (templates and daily instances) for that routine.

- POST `/routines/reorder`
  - Body: `{ routineIds: string[], childId: string }`
  - 200 → `{ success: true }`
  - Applies contiguous `order` values based on the array position for the child.

Task Templates (Routine definitions)

- GET `/templates?childId=...&routineId=...`
  - 200 → `Task[]` templates for the child/routine, sorted by `order`
  - Task = `{ id, routineId, ownerId?, childId, title, emoji, done, dueTime?, prime?: number[], order, isTemplate: true, updatedAt?, version? }`

- POST `/templates`
  - Body: `{ childId: string, routineId: string, title: string, emoji: string, dueTime?: string, prime?: number[] }`
  - 201 → created template `Task`

- PATCH `/templates/:id`
  - Body: Partial of Template Task (same shape as Task, excluding `id`, `ownerId`, `childId`, `isTemplate`)
  - 200 → updated template `Task`

- DELETE `/templates/:id`
  - 200 → `{ success: true }`

Daily Tasks (Instances)

- GET `/tasks?childId=...&routineId=...&date=YYYY-MM-DD`
  - 200 → daily `Task[]` where `isTemplate === false`, sorted by `order`
  - If tasks for `date` do not exist yet, the server SHOULD provide a way to generate them (see below). Choose either:
    - Option A: Auto-generate from templates on first GET for the date.
    - Option B: Require explicit generation via `/tasks/generate-daily` before first GET.

- POST `/tasks`
  - Body: `{ childId: string, routineId: string, title: string, emoji: string, date: YYYY-MM-DD, dueTime?: string, prime?: number[] }`
  - 201 → created daily `Task` (rarely needed if using generation route)

- PATCH `/tasks/:id`
  - Body: Partial daily task update e.g. `{ done?: boolean, title?: string, dueTime?: string }`
  - 200 → updated `Task`

- DELETE `/tasks/:id`
  - 200 → `{ success: true }`

- POST `/tasks/generate-daily`
  - Body: `{ date: YYYY-MM-DD, childId: string, routineIds?: string[] }`
  - 201 → `Task[]` created instances from templates for the given date (optionally restricted to specific routines)

- POST `/tasks/reorder`
  - Body: `{ routineId: string, childId: string, taskIds: string[] }`
  - 200 → `{ success: true }`

Rewards and Stars

- GET `/rewards`
  - 200 → `RewardRule[]` where `RewardRule = { id, ownerId?, name, cost }`

- POST `/rewards`
  - Body: `{ name: string, cost: number }`
  - 201 → `RewardRule`

- PATCH `/rewards/:id`
  - Body: Partial `{ name?: string, cost?: number }`
  - 200 → updated `RewardRule`

- DELETE `/rewards/:id`
  - 200 → `{ success: true }`

- GET `/stars?childId=...`
  - 200 → `{ stars: number }`

- PATCH `/stars`
  - Body: `{ childId: string, delta: number }`
  - 200 → `{ stars: number }` (updated balance)
  - Server must prevent negative balances.

Settings

- GET `/settings`
  - 200 → `Settings` where
    - `Settings = { mode: 'child'|'adult', theme: 'light'|'lowstim', userRole: 'child'|'parent'|'guardian', currentRoutineId?: string, currentChildId?: string, adminPin?: string }`
    - Server may persist only relevant fields; UI-only fields can be stored client-side.

- PATCH `/settings`
  - Body: Partial `Settings`
  - 200 → updated `Settings`

Health

- GET `/health`
  - 200 → `{ ok: true }`

Security and Authorization Rules
- Every request except `/auth/*` and `/health` requires a valid Bearer token.
- The token resolves to an owner account. All resources queried or mutated must be owned by that account.
- For routes with `childId`, the server must verify that the child belongs to the current owner.
- Do not leak existence of resources not owned by the requester.

Notes and Implementation Guidance
- Time-of-day smart selection is client-side; routines may later include a `type` field (`morning|after_school|bedtime`) to help the client choose deterministically.
- Reordering uses positional lists; server should normalize `order` to contiguous integers starting at 1.
- Daily task generation should be idempotent for the same `{ childId, date, routineId }` combinations.
- Timestamps: include `updatedAt` and increment `version` on writes to support optimistic concurrency if desired.

Example Error Responses
```json
{ "code": "NOT_FOUND", "message": "Routine not found" }
```
```json
{ "code": "UNAUTHORIZED", "message": "Missing or invalid token" }
```
